WordWrap (sgk_wordwrap, Python, GPLv3, ~2.9k lines of package code excluding tests) is hotkey-only, by explicit design: it never buffers keystrokes and never guesses. It has no text buffer, no dictionary, no language model and no scancode-to-character mapping at all. Its evdev listener only tracks modifier scancodes and the 4 configured trigger keys; the text to fix is obtained from the clipboard (Ctrl+Insert copy, with a UUID marker to detect "nothing selected"), converted char-by-char through JSON tables (en<->ru, en<->uk), pasted back with wl-copy + synthetic Ctrl+V through uinput, and the layout is then switched. Its "automatic keyboard layout switcher" docstring in __init__.py is a misnomer. So nothing in WordWrap can be lifted as an automatic mode.

On GNOME Wayland WordWrap learns the active layout purely via `gsettings get org.gnome.desktop.input-sources mru-sources` (first xkb tuple = active), with `sources` for the list and `current` only as a cold-start fallback, because GNOME Shell neither reads nor writes `current` in a live session. It switches with `gsettings set ... current <idx>`, verifies against mru-sources after 60 ms, and if that did not take effect presses the shortcut read from `org.gnome.desktop.wm.keybindings switch-input-source` (default Super+Space) via uinput until mru-sources matches. No D-Bus, no IBus calls, no xkbcommon, no focused-window API (it states that is unavailable to a normal client on GNOME Wayland, so its password-field blacklist is "best-effort only" = non-functional on Wayland).

gswitch already independently implements the same GNOME Wayland mechanism (gsettings switch-input-source detection + uinput replay + mru-sources confirmation), and in a more robust form (epoll, hotplug, own-virtual-device blacklist, session-env handling for Fedora dbus-broker, 10 ms/event replay instead of 300-800 ms clipboard settles). The only reusable knowledge from WordWrap for an auto-mode is: (1) read the CURRENT layout from mru-sources inside the daemon (gswitch's daemon only diff-checks mru-sources to confirm a toggle; current-layout reading exists only in the tray for the icon), (2) the explicit finding that the `current` dconf key is inert, and (3) the explicit finding that focused-window/password-field detection has no API on GNOME Wayland.

Feasibility of an auto mode in a gswitch fork: the input/output plumbing is already in place. The buffer (Converter) already holds scancodes + shift state, already finds the last word, already generates toggle + backspaces + replay, and already has an undo arm. The missing pieces are (a) an evdev-scancode -> XKB key name (`AD01`) table to render the buffered word as text under each of the two loaded layouts (gswitch has KeyMap keyed by XKB names from /usr/share/X11/xkb/symbols but no scancode->name table), (b) a cached current-layout reader, (c) a scoring function (dictionary / char n-gram) and a trigger on word-boundary keys, and (d) config keys. That is a moderate, well-bounded change (rough order: a few hundred lines of Go plus data files). The hard, unsolved parts are UX/safety, not plumbing: no focused-window detection on GNOME Wayland (password fields), keystrokes typed during the ~150-300 ms switch-and-replay window interleaving with the replay, mouse clicks not clearing the buffer, and per-window layout mode. An LLM per word is not practical (latency/privacy/offline); a local dictionary + character n-gram model is the realistic "AI".

### risks

- No focused-window / password-field detection on GNOME Wayland for a non-shell client: WordWrap documents this explicitly (detector.py:1-6, :79-86) and gswitch has no detector at all. An auto mode would also 'correct' text in password fields, terminals, IDE command palettes, etc. Mitigation needs a GNOME Shell extension or a per-app opt-out that cannot currently be enforced.
- Race between replay and continued typing: a correction fires on the space after the word; the user is already typing the next word. gswitch's toggle confirmation alone can take up to 2x20x50 ms (gnome_wayland_layout_switch.go:11-13) plus LayoutSwitchDelay 100 ms (config.go:58); physical keystrokes in that window interleave with synthetic backspaces at the compositor and corrupt text. EVIOCGRAB (input_reader.go:396-418) can mitigate but adds complexity and a stuck-grab failure mode.
- Mouse clicks do not clear the key buffer (only keyboards with KEY_A are opened, input_reader.go:220; BufKillers types.go:181-185 are keyboard keys), so after clicking into another field the 'last word' can span two fields and auto-correction would backspace into the wrong place. Punto relies on window hooks for this; none exist on Wayland.
- GNOME per-window layout mode (README.md:371-377 troubleshooting): mru-sources may not reflect the layout of the field being typed into, so the cached 'current layout' can be wrong and the auto mode would correct in the wrong direction. Requires per-window=false or extra validation.
- Accuracy of the decision function: ru/en share no letters so detection of 'ghbdtn' vs 'привет' is easy, but short words, abbreviations, URLs, identifiers, passwords typed in a terminal, mixed-language chat and transliteration produce false positives; every false positive costs the user an undo keystroke and breaks flow. A dictionary + char n-gram threshold needs tuning; an LLM call per word is impractical (latency, privacy, offline).
- gsettings subprocess per word to read the current layout costs 10-30 ms and spawns a process; without caching/dconf-notify it adds noticeable latency and CPU churn at typing speed.
- Punctuation differences between layouts (en_ru.json:73-79 shows '/'->'.', '#'->'№', '&'->'?') mean the scancode replay produces different punctuation after toggle; the scoring must render with the real XKB maps (gswitch LoadLayout) rather than letters only, or boundary punctuation will be converted unexpectedly.
- Fork maintenance burden: gswitch is actively released with CI, packaging (DEB/RPM/OBS), SELinux-tested on Fedora 44; a fork diverging in switcher.go/converter.go will need rebasing on every upstream release, or the feature must be upstreamed behind an opt-in flag (upstream README states manual-only as a design principle, README.md:9-10, :35-37).
### open_questions

- Does GNOME Shell keep mru-sources updated under per-window layout mode when focus changes between windows with different layouts, or only on explicit switches? This determines whether the cached current-layout is trustworthy (neither repo answers it; WordWrap only asserts it is updated 'on every real switch', layout_manager.py:155-156).
- Is the user willing to run with `org.gnome.desktop.input-sources per-window false` (gswitch README.md:377) for the auto mode to be reliable?
- What decision model is acceptable to the user: a static hunspell-style word list (/usr/share/myspell ru_RU/en_US on Fedora) plus character n-grams, or does 'AI' mean a local small model? Any network LLM per keystroke is ruled out by latency and privacy; is an offline model acceptable?
- Is the fork meant to be upstreamed (opt-in `auto-correct` flag, matching gswitch's existing config style) or kept private? Upstream explicitly markets 'manual and deterministic', so acceptance is uncertain.
- How should the auto mode behave in terminals and IDEs where backspace/replay semantics differ (WordWrap needed a separate terminal flow, text_processor.py:165-208), given that no app detection is possible on Wayland? A global pause hotkey plus the existing undo may be the only practical answer.
- Should mouse devices be opened (BTN_LEFT) to clear the buffer on click, and does the packaged udev/uaccess ACL already cover pointer event nodes?

Verdict: adding an automatic mode to gswitch is architecturally straightforward (the whole erase→switch→retype machinery already exists and can be reused verbatim via performConversion(ActionConvertWord)), but the daemon is missing three inputs an auto-corrector needs: (1) it never knows the CURRENT layout — it only blindly toggles via the detected hotkey; (2) it never knows the CHARACTERS typed — the buffer holds raw evdev scancodes plus Shift down/up events, and the runtime has no scancode→XKB-keyname table (the rune maps in layout.go are keyed by XKB names like <AD01>); (3) it has no mouse/focus knowledge (only keyboard devices with KEY_A are opened; the README's "mouse click resets buffer" claim is not implemented). Everything else is plumbing: a word-boundary hook in processKeyEvent (switcher.go:677-719), a `LastWord()` accessor on Converter mirroring the scan at converter.go:517-534, an offline language scorer (hunspell wordlists or char n-grams, ~tiny), a config flag, and a dconf/gsettings watcher for the active layout.

Mechanics confirmed from code: evdev devices are opened passively (O_RDONLY|O_NONBLOCK, no EVIOCGRAB — GrabAll exists but has no callers), so physical keystrokes always reach the compositor; replay happens synchronously on the main loop goroutine while the reader goroutine keeps queuing new physical events, and after replay `inputReader.Flush()` throws away whatever is still in the kernel fd queue. A 7-key word costs ~30 synthetic events × 10 ms + 2×100 ms layout delays + GNOME-Wayland gsettings polling ≈ 0.5-0.7 s of visible backspace/retype, during which any key the user types is interleaved into the app. In manual mode the user chooses the moment; in auto mode this race fires on every corrected word, so a fast typist's next word will routinely collide. The layout switch on GNOME Wayland is emitted as Super+Space (first accelerator from org.gnome.desktop.wm.keybindings switch-input-source) and confirmed by polling `gsettings get mru-sources` (process spawn, 50 ms × up to 20 × 2 attempts). The trailing Space after the word is part of the erased+retyped range; ENTER events in the range are replayed too, so an auto trigger on Enter would re-send Enter (double submit) — auto mode must fire on Space only unless the daemon becomes a full grab-and-reemit proxy (a much bigger rewrite).

Maintainer intent: README positions the tool as explicitly "manual and deterministic", "does not guess your language or change text in the background" (added in commit ce0d99c "docs: clarify project positioning"); CONTRIBUTING says development happens in a private tree, releases land as single squashed commits and PRs are not merged directly. So an auto mode is a fork to maintain, not a feature to upstream. There are no TODO/FIXME comments about auto mode anywhere.

Feasibility for me: the core fork (hook + scancode→char table + scorer + config flag + tests) is roughly 600-1000 lines of Go and is realistic in a few working sessions; the time sink is robustness — the replay race, false positives on logins/acronyms/code/mixed-language chat, password fields, IBus/readline/vim contexts, and learning the current layout on GNOME Wayland (GNOME per-window layout mode makes this worse). ### risks

- Replay race becomes routine: devices are not grabbed (input_reader.go:214, GrabAll unused) and the ~0.5-0.7 s erase/switch/retype runs synchronously on the main goroutine (switcher.go:823-920) while the user keeps typing; physical keys typed during the replay are delivered to the app interleaved with synthetic ones and in whichever layout happens to be active mid-toggle. Manual mode only hits this when the user chooses to trigger; auto mode hits it on every corrected word.
- Enter as a boundary is unsafe: the Enter has already been delivered to the app before gswitch sees it (no grab), and Convert's replay range includes trailing ENTER events (converter.go:517-534 + :579-596), so an auto-correction after Enter would both edit the wrong line and re-send Enter (double submit in chats/terminals). Fire on Space only, or rewrite gswitch as a grab-and-reemit proxy (large change, touches every keystroke on the system).
- Unknown current layout: the daemon only toggles (converter.go:506-512) and never reads the active layout except as a before/after check via a gsettings process spawn (gnome_wayland_layout_switch.go:28-41). Auto mode must track it; GNOME's per-window layout mode (README.md:370-377) makes any cached value go stale on focus change.
- One-backspace-per-key assumption (converter.go:558-566) breaks under IBus preedit, dead keys, IDE autocomplete, readline/vim modes, terminal apps with their own line editing, and especially password fields — in auto mode the daemon would retype passwords through the converter and could destroy text. Manual mode lets the user avoid those contexts; auto mode cannot tell where focus is (no compositor connection on Wayland).
- No mouse/focus awareness: mice are never opened (input_reader.go:220), so a click mid-sentence does not reset the buffer; the backspace count can then delete characters that were not part of the word (README.md:75 claim is not implemented).
- False positives on short words, logins, acronyms, code identifiers, URLs and mixed-language chat ('ok', 'lol', 'git', 'sudo' inside Russian text); every misfire costs a visible flicker plus a wrong layout left active (the toggle is never reverted). A whitelist, a minimum word length, a confidence margin and a reliable undo are mandatory, not optional.
- Visible latency: Delay=10 ms per event and LayoutSwitchDelay=100 ms twice (config.go:57-58, switcher.go:905-916) plus gsettings polling means each correction is a half-second animation of backspaces; lowering delays risks dropped events (comment at switcher.go:855-857 explains GNOME drops keys arriving mid-switch).
- CapsLock state and Shift state are only partially known (CapsLock 58 is ignored; Shift is tracked via buffered events), so case-sensitive scoring is unreliable — score case-insensitively.
- Fork maintenance: upstream lands as squashed release commits and does not merge PRs directly (CONTRIBUTING.md:7-17), and the maintainer explicitly positions the product as manual (README.md:8-10, :35-36, commit ce0d99c). Every upstream release means a rebase of the auto-mode patch; expect no upstream adoption.
- 'AI' must stay local: README.md:83 and SECURITY.md promise zero network code; sending every typed word to a cloud model from a daemon with raw keyboard access is unacceptable and also too slow. A local neural model in Go would add heavy cgo/ONNX deps to a 10 k-line, dependency-light project; n-gram tables or hunspell lookups are the realistic 'AI'.
- The Flush() at switcher.go:917 and the reader goroutine both read the same non-blocking fds (input_reader.go:357, :386); which one wins is nondeterministic, so some physical keystrokes typed during replay are dropped from gswitch's buffer but not from the app — the buffer and screen diverge, which in auto mode compounds across consecutive words.

### risks

- Characters typed during an automatic replay are dropped: handleIncomingEvent ignores events while inConversion (switcher.go:1139-1143) and conversion sleeps Delay per emitted event plus LayoutSwitchDelay (switcher.go:905-916); a fast typist will lose keystrokes unless the hot path is redesigned to queue and replay.
- Latency on GNOME Wayland: switch confirmation can poll up to 2×20×50 ms = 2 s (gnome_wayland_layout_switch.go:10-13) plus LayoutSwitchDelay 100 ms twice; acceptable for a manual trigger, disruptive when fired automatically on every suspicious word.
- No per-application exceptions are possible without new architecture: the daemon works below the display server and has zero focused-window knowledge (README.md:28-31; buffer is only cleared on killer keys, types.go:181-185). Exceptions can be lexical only (regex/word list) unless a GNOME Shell/D-Bus focus probe is added, which the security model discourages.
- False positives on passwords, URLs, code, identifiers and short chat tokens; a wrong auto-correction in a password field is worse than any manual-mode inconvenience. The existing undo (converter.go:613-641) covers only the immediately preceding identical action.
- 'AI' is constrained to a local statistical model: no network (SECURITY.md:24-25; gswitch.service:36 RestrictAddressFamilies=AF_UNIX AF_NETLINK), MemoryDenyWriteExecute=true (gswitch.service:35) blocks JIT-based ML runtimes, ProtectHome=read-only (:25) blocks learning into ~/.config without a unit change. Accuracy will be Punto-class, not LLM-class.
- Current-layout detection in the daemon does not exist; the gsettings mru-sources read spawns a process per word (gnome_wayland_layout_switch.go:26-41). mru-sources is empty until the first switch after login (tray/layout_monitor.go:313 comment), so a fallback is needed. If layout is changed via mouse/tray/IBus panel the daemon must re-read rather than track toggle parity.
- Maintenance of a fork: upstream publishes squashed release commits only and does not merge PRs (CONTRIBUTING.md:5-17); the auto-mode touches the two largest and most-changed files (switcher.go 1242 lines, settings_window.go 1707 lines), so every upstream release means a manual rebase with conflicts.
- Maintainer's stated philosophy is explicitly anti-automatic (README.md:8-10, :35-36); expect an auto-mode to be rejected upstream, so the work has no path to 'landing' and all packaging/updates stay on the user.
- Lint gate is strict (35+ linters, funlen 150, gocognit/gocyclo 45, nestif 5, revive exported-comments, ireturn; .golangci.yml:27-234); new files get no per-file exemptions (:284-300). Keeping CI green in the fork is extra effort, though CI itself is optional for a personal fork.
- No fake uinput/evdev harness exists (uinput.go:12-32 concrete; uinput_test.go:5-16 trivial), so the emit path is untested today; an auto-mode adds risk precisely in that path. Adding a keyEmitter interface is a prerequisite for safe testing.
- GTK unit tests require Xvfb and GSWITCH_GTK_TEST=1 (tray/modifier_swap_test.go:17-19); CI only runs a Python smoke test (ci.yml:50-54), so UI regressions in the fork may go unnoticed.
- Dictionary data: Russian+English word lists must be bundled in the RPM (size, licensing of the source corpus) and loaded at daemon start; memory and startup time increase for a process that is currently tiny.
- Binary/paths are hardcoded for pkexec and polkit (/usr/bin/gswitch in tray/gswitch_binary.go:39-44 and com.github.arumata.gswitch.policy:19-20); renaming the fork's binary or package requires coordinated changes in nfpm, polkit policy, desktop files and systemd unit (.goreleaser.yml:107-171, configs/gswitch.service:17).
- Word-boundary semantics differ between layouts: Convert() splits on KEY_SPACE/ENTER only (converter.go:516-534); punctuation scancodes (e.g. 51 comma, 52 dot) that are letters in ru (б, ю) stay inside the 'word', which is exactly the Punto-style ambiguity an auto decider must handle.
### open_questions

- Trigger policy: fire only on SPACE/ENTER, also on punctuation, or after an idle timeout (e.g. 300 ms with no key)? This decides how much of converter.go:516-534 word-boundary logic must change.
- Should auto-correction leave the system layout switched (true Punto behaviour: 'you meant to be in Russian') or switch back after replaying the word? performConversion only toggles once (converter.go:506-512); switching back doubles the GNOME-Wayland confirmation cost.
- Decision model and accuracy target: hunspell-style word lists (exact-match), letter-bigram statistics per language (Punto's classic approach, tiny data), or a small n-gram LM? What false-positive rate is acceptable before the user turns it off?
- Does the user want an adaptive/learning dictionary written to ~/.config? That requires relaxing ProtectHome=read-only / adding ReadWritePaths (configs/gswitch.service:25-28) and sits uneasily with 'no persisting of keystrokes' (CONTRIBUTING.md:50-53) — words, not keystrokes, but still typed content on disk.
- Exceptions scope: lexical patterns only (regex + word list in config), or is the user willing to accept a GNOME Shell extension / D-Bus probe for focused-window app-ids to get per-application disabling (terminals, password managers, IDEs)?
- Current-layout source on the user's GNOME 50 Wayland: is a gsettings spawn per word acceptable, or should the fork track toggle parity from observed layout-switch key presses (cheap, but drifts when layout changes via mouse/IBus panel)? Test needed on the actual machine.

- Undo UX in auto-mode: is 'repeat the trigger' (manual double-Shift) sufficient to revert an unwanted automatic correction, or is a dedicated 'undo auto' key / toast needed? - How does the user handle the dropped-keystroke problem during replay today (manual mode) — does Delay=10 ms/LayoutSwitchDelay=100 ms already feel slow on their machine? That calibrates whether a queue-and-replay rewrite is mandatory for auto-mode.

## read:punto-rs-engine

### summary

Feasibility: a gswitch fork with a punto-rs-style automatic mode is realistic, and the "AI" part is the cheapest piece. punto-rs's detector is ~300 self-contained lines (trigram letter model + Bloom dictionary + closed short-word lists + exception list), with a labelled 2403-row evaluation set and tuned thresholds, all MIT/BSD/public-domain and portable to Go with ~5.4 MB of embedded model blobs. The hard parts are everything around the detector, and they are exactly where punto-rs gave up on GNOME: (1) knowing which layout is active right now — punto-rs reads it only from KDE's session D-Bus org.kde.keyboard (signals layoutChanged/layoutListChanged, methods getLayoutsList/getLayout) and silently disables auto mode when that service is absent; GNOME has no equivalent public API, and gswitch today only reads it in the tray by spawning `gsettings get org.gnome.desktop.input-sources mru-sources` every 500 ms; (2) the retype must happen on every space of a mis-typed word, so punto-rs grabs the keyboards (EVIOCGRAB), queues keys typed during the fix and replays them, waits for full key release (+30 ms), uses 1 ms inter-key delay and ends the switch wait early on KDE's signal — gswitch has none of this (no grab in the word path, 10 ms/event, 100 ms switch delay, GNOME-Wayland confirmation by polling gsettings up to 2×20×50 ms); (3) a word followed directly by Enter cannot be auto-fixed with passive evdev on Linux (punto-rs does it only on Windows via a hook), which is the chat/messaging case; (4) no per-app exclusions on GNOME Wayland (punto-rs needs a KWin script for the active window). Verdict for the two options: gswitch out-of-the-box = manual, deterministic, already validated on Fedora 44/GNOME 50 Wayland; fork = several weeks of focused work (detector port ~2 days; GNOME active-layout state tracking + validation ~1 week; grab/queue/release-wait and latency work ~1 week; config/exceptions/undo/tray ~2-3 days; real-session validation open-ended), yielding a Space-triggered corrector with ~95% recall / 0 false fixes on punto-rs's held-out set but inherent gaps (Enter case, terminals/password fields, GNOME switch latency). Upstream gswitch explicitly rejects guessing language or changing text in the background, so this would be a long-lived fork, not a PR. ### risks

- Active-layout feed on GNOME is the central unsolved piece: GNOME exposes no org.kde.keyboard-like D-Bus API; gswitch's only source is dconf key `mru-sources` read by spawning `gsettings` (500 ms poll in the tray, 50 ms polls in the Wayland confirmation). At every-Space cadence this is too slow and too expensive; an in-process GSettings/dconf client with change notification or local state tracking (own switches + observed user chord) is required and unvalidated. GNOME's per-window input-source mode (gsettings per-window) silently breaks local state tracking ($GSWITCH/README.md:370-377).
- Latency and ordering on GNOME/IBus: gnome-shell applies the switch asynchronously and drops key events arriving mid-switch ($GSWITCH/internal/gswitch/runtime/switcher.go:855-857; $PUNTO/README.md:345); punto-rs needs a 120 ms wait with no early-exit signal on GNOME, gswitch uses 10 ms per event + 100 ms + polling — an auto fix of a 6-letter word costs ~0.3-0.5 s during which the user keeps typing.
- No grab/queue in gswitch's word path: keystrokes typed during the retype interleave with injected Backspaces/replay in the application (punto-rs solves this with EVIOCGRAB + replay queue, $PUNTO/src/daemon.rs:36-99); adding it also inherits punto-rs's refusals (another grab holder, a key still held, $PUNTO/src/devices.rs:54-63).
- Enter-terminated words are not auto-correctable with passive evdev on Linux ($PUNTO/src/devices.rs:70-72, README 237-240): 'ghbdtn⏎' in a chat goes out uncorrected; fixing this needs a permanently grabbing design (which punto-rs's README 44-49 says cost Easy Switcher lost keystrokes) or an IM-level approach — a different project.
- No per-app exclusions on GNOME Wayland (punto-rs relies on a KWin script, $PUNTO/src/kwin.rs:1-3): terminals, IDEs and password managers get the same auto fixes; the detector's dictionary gate and 20-word exception list keep the labelled code/terms/translit classes at 0 false fixes, but the user's own slang/commands will need a corpus-grown exception list ($PUNTO/src/layout/AGENTS.md:12).
- Inherent detector limits: 3+ letters only, digits never, 1-letter never, 2-letter by closed lists, ≈5% misses, ~1% Bloom false 'known'; hard-coded keymaps for us/ru/ua(unicode) only; any ru variant accepted unchecked ($PUNTO/src/kde.rs:32).
- Retype is not atomic and never rolled back; a fix cancelled by a click/focus change leaves half-edited text ($PUNTO/README.md:159-165, 368-369); auto mode multiplies exposure to this versus a manual trigger.
- Security/privacy posture: both daemons already buffer every keystroke in memory; auto mode adds no exfiltration path but injects synthetic keystrokes unattended, including into password fields it cannot recognise ($PUNTO/README.md:365-367; $PUNTO/docs/release-validation.md:125-128).
- Maintenance: the fork diverges from gswitch's stated 'manual and deterministic' principle ($GSWITCH/README.md:8-10, 35-36), so changes will not be upstreamed; two code paths (Go port of a Rust detector + Go eval harness) must be kept in sync with punto-rs improvements by hand; binary grows by ≈5.4 MB.
- 'AI for accuracy' expectations: per-keystroke LLM calls are infeasible (latency, privacy); the realistic accuracy lever is a larger local n-gram/word model plus a bigger exception corpus, and punto-rs's own rule is that thresholds change only after re-evaluation on the labelled set ($PUNTO/src/layout/AGENTS.md:3, 10).
- Session-safety work not present in gswitch for the auto path (punto-rs's logind guard: seat0, Active, LockedHint, Remote, 2 s staleness, $PUNTO/src/session.rs:141-212) — an auto mode that fires on a lock screen or in another user's session is worse than a manual one.

### risks

- Перемешивание ввода: нет захвата клавиатуры (GrabAll не используется, input_reader.go:396-418), коррекция занимает ~0.5 с при delay=10/layout-switch-delay=100 (switcher.go:854-917) — клавиши, нажатые в это время, попадут в приложение между backspace'ами и реплеем. Решение (grab + ре-инжект) — самая рискованная часть: баг или падение демона с захваченной клавиатурой = «мёртвая» клавиатура до ungrab.
- Ложные срабатывания классификатора — главный UX-риск: короткие слова, транслит, смешанный текст, код/терминал (ls, cd, имена переменных), пароли. На Wayland демон не знает окно в фокусе и не видит кликов мыши (input_reader.go:220; нет BTN_*), поэтому «не исправлять в терминале/в пароле» без расширения GNOME Shell реализовать нельзя; буфер может быть устаревшим после смены фокуса мышью, и авто-коррекция сотрёт текст не там.
- Источник активной раскладки на GNOME Wayland — только gsettings mru-sources через fork/exec (gnome_wayland_layout_switch.go:26-41; session_env.go:724-735): дорого для частых запросов, не событийно; локальный трекер по хоткею рассинхронизируется при переключении через меню в топ-баре, per-window режиме (у пользователя сейчас false) или смене раскладки другим инструментом; нужен ресинк по DBus-сигналу (IBus/dconf), что не проверено на GNOME 50 в живую.
- Надёжность реплея аккорда: модификаторный хоткей (<Alt>Shift_L на хосте) эмитится через uinput; при неподтверждении изменения mru-sources за 2×1 с конверсия отменяется (switcher.go:872-875) — в авто-режиме это будет происходить чаще и незаметно для пользователя; Super+Space на Wayland не имеет обходного пути, в отличие от X11 (gnome_x11_binding.go).
- Авто-режим противоречит философии и security-модели апстрима (README.md:35-36; CONTRIBUTING.md:7-16): PR не примут, форк придётся сопровождать самостоятельно и вручную переносить каждый squash-релиз; инъекция ввода без явного намерения пользователя расширяет поверхность ущерба от багов (SECURITY.md:24 и далее).
- «ИИ для точности» через облачную LLM невозможен без слома принципа «no network» и отправки всех нажатий наружу; локальная ML-модель на каждое слово должна укладываться в единицы мс — практичны только словари + n-граммы (как в Punto/xneur), а не нейросеть.
- Парсер XKB регэкспом построчно (layout.go:376-378,475-491) и без include из других файлов (:465) — для us/ru basic работает (release-gate), но для нестандартных вариантов/многострочных определений таблица будет неполной, и рендер слова окажется неверным; CapsLock не отслеживается (types.go) — регистр при рендере может быть ошибочным.
- Задержка/мерцание: при каждой авто-коррекции слово стирается и перепечатывается ~0.5 с; снижение delay ниже 10 мс апстрим считает ненадёжным (комментарии switcher.go:855-857, config template :509-513).

## read:detection-algorithms

### summary

Verdict: forking gswitch and adding an opt-in automatic (Punto-like) mode is feasible and well-scoped for a GNOME-50/Wayland/IBus, us+ru-only target — roughly 2–3 weeks of part-time work for a usable first version, most of it in input-grabbing/replay robustness rather than in the language model. The "AI" part should NOT be an LLM in the hot path: the on-space decision must run in microseconds, and a tiny per-language letter-trigram model plus Bloom-filter dictionaries (the design punto-rs already ships and evaluated: 0 false corrections on 360 must-not-touch words, 194/205 ≈ 94.6% recall on ≥3-letter words) is the right tool. An LLM is only sensible as an offline/slow-path helper (mining the user's manual corrections/undo events into an exceptions list, or reviewing a line after Enter), and even that collides with gswitch's privacy posture (no network, keystrokes never on disk) and its hardened systemd unit.

Shorthand used in evidence below: GS = /tmp/claude-1000/-home-vab--config-Claude-scratch-workspaces-fa1b9472-8084-4209-ae23-da2ad8a448d8-aafa8dfb-8eb5-4dfd-8581-78d771697042-scratch-2026-10-09-c4bd00/45587cb4-d523-4454-9856-1f18254bad93/scratchpad/repos/gswitch ; PR = same prefix .../repos/punto-rs.

What gswitch gives you for free: a working evdev reader with hotplug, a scancode buffer that already contains Space/Enter and tracks Shift state and Backspace, a word/phrase boundary finder, a replay engine through uinput, GNOME-Wayland layout-switch confirmation, XKB symbol parsing for us/ru, a tray with settings, packaging for Fedora, and a godbus dependency. What is missing for auto mode: (1) a trigger on Space/punctuation instead of double-Shift; (2) knowledge of WHICH layout is active (manual mode just toggles, auto mode needs direction) — on this machine IBus's private bus exposes GetGlobalEngine and GlobalEngineChanged(s engine_name), and `ibus engine` returns xkb:us::eng, so an in-memory tracker is cheap; (3) a scancode→character table for both layouts (gswitch parses XKB symbols by <AD01>-style names but has no evdev-code→name map); (4) the detector itself (~300 lines in punto-rs: trigram cost per char, margin ≥1 bit/char, alt-layout word must be in the other dictionary and the on-screen word must not be, min 3 letters, exceptions list); (5) EVIOCGRAB + capture/replay of physical keys during the ~0.3–0.6 s correction (gswitch has GrabAll/UngrabAll but never calls them; its default 10 ms inter-event delay × ~30 events + 2×100 ms layout-switch pauses means a 6-letter word costs ≈0.5 s, during which the user's next keystrokes would interleave with the synthetic backspaces/replay); (6) per-app exclusion (terminals, password managers) — hard on GNOME Wayland: GNOME 50 here has no org.gnome.shell `introspect` key, so this needs a Shell extension or is replaced by a pause hotkey; (7) config keys, tray toggle, "don't correct this word" menu, undo via the existing manual trigger.

Option comparison for the user: (A) gswitch as-is: zero risk, manual double-Shift, nothing to maintain. (B) own fork: real automation for RU/EN with high precision at the cost of a permanent fork (upstream merges nothing directly and positions the product as explicitly non-guessing), a changed security story (grabbing keyboards during correction, a learned exceptions file in ~/.config), and a long tail of false positives in terminals/code/slang that must be handled by exclusions and a pause key. A middle path worth considering: port/embed punto-rs's already-trained ru/en models (MIT + hunspell-ru BSD) into the fork instead of designing a new classifier; the model files are 36 KB + 1.7 MB (ru) and 20 KB + 444 KB (en).

### risks

- Interleaving: without EVIOCGRAB the ~0.5 s correction (10 ms × ~30 events + 2×100 ms + GNOME poll) lets the user's next keystrokes land between synthetic backspaces and replayed keys, producing garbled text in the focused app — in manual mode the user is waiting, in auto mode they are mid-sentence. Fixing it means grabbing all keyboards during correction and replaying captured input afterwards (punto-rs's design), which is the riskiest new code in the fork (stuck synthetic keys, lost events if the daemon dies mid-replay, hotkeys like Ctrl+C delayed under the grab).
- Lowering gswitch's 10 ms per-event delay to approach punto-rs's 1 ms may make GNOME Wayland drop events around the asynchronous layout switch (gswitch's own comment at switcher.go:855-857); needs measurement on GNOME 50 before changing defaults.
- Enter cannot be held back on Linux evdev: an auto-correction triggered on Enter in Telegram/Slack would fire after the message is sent and type the corrected word into the now-empty input (and possibly send it). Default must be Space/punctuation triggers only.
- Direction errors: if the active-layout tracker desynchronises (IBus restart, layout toggled from the top-bar menu, future per-window mode), the daemon will convert correctly-typed words into garbage with full confidence; needs re-read of GetGlobalEngine/mru-sources after each correction and a hard disable when the pair is not exactly us+ru.
- False positives in terminals, code editors and password prompts are the dominant real-world failure (xneur/Punto reputation); punto-rs's exceptions list (jq, tls, gtk, dnf…) shows the tail is tool-specific and must be curated per user. On GNOME Wayland there is no stable focused-window API (no `introspect` key on GNOME 50), so per-app exclusion needs a Shell extension or users must rely on a pause hotkey.
- Passwords: evdev cannot distinguish password fields; a correction inside a password prompt both corrupts the password and reveals its structure to the uinput stream. Punto relies on Windows APIs for this; the fork can only offer pause/exclusions.
- Stale buffer after mouse-driven focus changes: gswitch does not see mouse clicks (keyboard-only device filter), so an auto-correction may backspace characters belonging to a different field; mitigations (track BTN_* devices, buffer timeout like punto-rs's 30 s) add scope.
- Privacy/security posture changes: learning exceptions from undos means writing corrected words to disk (contradicts README 'keystrokes never touch the disk' and ProtectHome=read-only); any LLM-based slow path would add a network or model dependency the daemon's unit forbids and the README promises against — it would have to live in a separate opt-in process fed only with already-corrected/undone words.
- Maintenance: upstream merges nothing directly and ships squashed release commits; the fork will have to rebase an invasive change (hot path, grab/replay, tray) on each release, and the auto mode contradicts the project's stated philosophy, so upstreaming is unlikely.
- Recall ceiling: 1–2-letter words (в, и, я, он / a, I, is) cannot be decided by letter statistics and are handled only by frequent-word lists tied to the following corrected word; Bloom filters have ~1% false 'known' rate, and /usr/share/dict/words contains many obscure tokens that will suppress RU→EN corrections unless filtered.
- Layout coverage: a hardcoded 47-key scancode→char table (the fast route) is correct only for the standard us and ru(winkeys) layouts; users with ru(typewriter), ua, de etc. would need the XKB-parsed path and new models, and more than two layouts are unsupported by gswitch already.
- Timing regressions in the manual path: adding detector calls and grab/replay to processKeyEvent must stay off the per-keystroke path except on Space; otherwise latency hits every key on the single event goroutine.
### open_questions

- Scope decision: GNOME-only (IBus GlobalEngineChanged + gsettings fallback) first, or also KDE (org.kde.keyboard like punto-rs) and fcitx5 from the start? Each backend is its own active-layout tracker.
- Trigger set: Space only (punto-rs), or also punctuation (bzz: . , ! ? ; : ' ")? Enter deliberately excluded on Linux — acceptable to the user that chat messages sent with a wrong-layout word are not fixed?
- Model source: embed punto-rs's trained ru/en .bin/.bloom files directly (MIT + hunspell-ru BSD + public-domain words — licence-compatible) or retrain in Go with the same recipe; and is a personal corpus (user's own chat history) acceptable for mining exceptions given the privacy stance?
- Grab policy: grab all keyboards for the whole correction (punto-rs) vs. a shorter grab only around backspaces; what per-event delay does GNOME 50 Wayland tolerate (1 ms? 3 ms?) — needs an experiment with the existing --debug mode before committing to timings.
- Undo/learning UX: should an immediate manual trigger after an auto-fix (a) only revert, (b) revert and add the word to exceptions, or (c) revert and offer a rule after N consecutive undos (Punto's model)? Where is the exceptions file stored given ProtectHome=read-only?

- Is a slow-path 'AI' feature actually wanted (e.g., a separate opt-in helper that periodically reviews undone/corrected words with a local model and proposes rules), given it cannot touch text retroactively on Linux and would need a relaxed privacy story?
- Would the user accept the alternative of running punto-rs itself (Rust, auto mode currently KDE-only) if its author adds a GNOME layout backend — i.e., is extending punto-rs (where the detector and grab/replay already exist) a cheaper path than extending gswitch (where tray/packaging/GNOME verification already exist)?

### risks

- Password fields: without the Shell extension (or AT-SPI, which is disabled: org.a11y.Status IsEnabled=false), auto mode cannot tell a password entry from a text box; a password that looks like a wrong-layout word (e.g. 'ghbdtn') would be silently rewritten. Terminal prompts (sudo) share the risk. The purpose information exists only inside gnome-shell (libshell-18.so 38852-38856) or via AT-SPI after enabling accessibility.
- Focused-window exclusions depend on a self-maintained GNOME Shell extension; org.gnome.Shell.Introspect is AccessDenied (allowlist = portal backends), the `introspect` gsettings key no longer exists on GNOME 50, and unsafe mode is off. Extensions break across GNOME major versions and get disabled on Shell crashes/updates.
- Stale key buffer: gswitch reads only keyboard devices (input_reader.go:172-200) and clears the buffer only on BufKillers (types.go:181-185); mouse clicks/focus changes are invisible, so an automatic trigger could 'correct' text in a different field than where it was typed. Manual mode tolerates this because the user triggers it; auto mode does not.
- Race between app and daemon: keys reach the application and gswitch concurrently (no EVIOCGRAB); the correction (backspaces + replay, 10 ms per key, 100 ms switch delay per default.conf:9-10) can interleave with fast typing or slow apps; the existing GNOME-Wayland comment (switcher.go:855-857) notes events get dropped mid-switch.
- Accuracy: dictionary-only decisions fail on names, slang, abbreviations, code, transliteration and mixed-language text; false positives are far more annoying than misses, so a confidence threshold plus an easy undo (converter.go:613-640) is mandatory. An ML/LM scorer adds latency, binary size and training-data work; it must run in a few ms per word to feel instant.
- Requires root to install the udev uaccess rule (configs/70-gswitch.rules) and the polkit policy; currently the user has no access to /dev/input or /dev/uinput (root:input 0660, no ACL, groups vab,wheel). SELinux enforcing on Fedora: upstream claims Fedora 44/GNOME 50 Wayland is tested (README table), but a fork with D-Bus/IBus access and a systemd unit using ProtectHome=read-only (configs/gswitch.service:25) must be re-verified.
- Dependence on IBus: GlobalEngineChanged only exists while ibus-daemon runs (pid 1440 now); gnome-shell sets `_disableIBus` inside PASSWORD fields (43754-43760), so engine signals may not track layout changes there; fallback to dconf `ca.desrt.dconf.Writer.Notify` on mru-sources covers only interactive switches (43602-43603).
- Build environment: Go is not installed; the tray needs cgo with gtk3-devel and libX11-devel (missing); maintaining a fork of a 27k-line Go project with its CI/goreleaser/OBS packaging (.github/workflows, packaging/opensuse) is ongoing work beyond the core change.
- The user's xkb-options value 'grp:shift_alt_toggle' is not a valid xkeyboard-config option (not in evdev.lst); harmless on GNOME (switching is done by the Shell keybinding) but any logic that trusts xkb-options for the hotkey would misdetect.
- The RemoteDesktop portal alternative to uinput (version 2, NotifyKeyboardKeycode) avoids udev rules but shows a consent dialog per session unless restore tokens are used, and still does not solve focus/password detection.
### open_questions

- Runtime confirmation that `GlobalEngineChanged` is emitted for xkb->xkb switches on this exact setup was not obtained because no keys may be pressed during probing; the Shell code path (activateInputSource -> setEngine -> set_global_engine_async) says yes, but it should be verified once by watching the signal while the user presses Alt+Shift.
- Does `_ibusManager.setEngine` short-circuit when the engine id is unchanged or while `_disableIBus` is set (password fields), and how does that affect a daemon that mirrors layout state from the IBus signal? Needs a read of the ibusManager.js `_setEngine` body (libshell-18.so strings 45677-45705).
- Which focus-signal design: the extension pushing a D-Bus signal on every focus/purpose change (lowest latency, lets the daemon clear its buffer) versus the daemon querying before each correction (simpler, adds a round-trip of a few ms).
- Should auto mode keep gswitch's passive-read architecture (app sees the wrong-layout word, then it is erased and retyped, Punto-style) or move to an exclusive evdev grab with full keystroke proxying through uinput (no flicker, but every key passes through the daemon and any crash or lag blocks typing)?
- Scoring approach: hunspell en_US/ru_RU lookup plus bigram heuristics versus a trained character n-gram or small neural classifier; what corpus, what threshold, and whether to also consider the previous words' language for context.
- Whether to enable AT-SPI (org.a11y.Status IsEnabled) as a second source for password/terminal detection — it is a user-visible accessibility setting change with its own performance/privacy implications, and GTK4/Qt only publish trees when enabled.
- Does the correction behave acceptably in Electron/Chromium, Firefox and XWayland apps on this box (text-input purpose availability differs per toolkit)?
- Fork strategy: maintain a long-lived fork with upstream merges, or propose an opt-in `auto-mode` upstream to arumata/gswitch (README positions the project as deliberately manual, so upstream acceptance is uncertain).
